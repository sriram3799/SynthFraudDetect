# SentinelStream: Synthetic E-Commerce Fraud Detection

## Overview

**SentinelStream** is a high-performance data engineering pipeline designed to identify fraudulent e-commerce transactions in real-time. By simulating high-frequency transaction streams, the application solves the "detection gap" where traditional batch-based fraud analysis fails to stop malicious actors before a transaction clears. 

The system utilizes **Apache Flink** for stateful stream processing—calculating risk scores and velocity patterns on the fly—and persists data into an **Apache Iceberg** lakehouse on **AWS S3**. By leveraging **DuckDB** and **dbt**, fraud analysts can perform forensic deep-dives with sub-second latency, ensuring that security teams can iterate on detection logic as quickly as fraud patterns evolve.



## Goals

1. **Instantaneous Flagging:** Target an end-to-end detection latency (p99) of under **80ms**, allowing the system to provide "allow/decline" signals in real-time.
2. **High-Scale Resilience:** Sustain a processing load of **25,000 synthetic transactions per second**, mimicking the peak traffic of a global e-commerce enterprise.
3. **Forensic Agility:** Enable analysts to run complex SQL aggregations on live data via **DuckDB**, reducing the time to discover new fraud vectors from hours to seconds.

## Core User Flow

1. **Infrastructure Provisioning:** Deploy the entire stack (Kafka, Flink, S3, EC2) using **Terraform** to ensure a consistent, secure **AWS** environment.
2. **Synthetic Generation:** A Python-based generator streams realistic e-commerce traffic—including "location-jump" and "rapid-fire" fraud patterns—into **Apache Kafka**.
3. **Pattern Detection:** **Apache Flink** processes the stream, comparing incoming transactions against historical user state to calculate immediate risk scores.
4. **Lakehouse Persistence:** All transactions and their associated risk metadata are written to **Apache Iceberg** on **S3**, providing a transactional audit trail.
5. **Analytical Modeling:** **dbt** models the raw data, calculating high-level metrics like "Daily Fraud Volume" or "Top Attacked Merchants."
6. **Forensic Querying:** Security analysts use **DuckDB** to query the Iceberg tables, performing rapid investigations into flagged accounts or IPs.

## Features

### Real-Time Detection Engine
* **Stateful Processing:** Uses Flink's managed state to remember user history (e.g., last known IP) without hitting an external database.
* **Velocity Checking:** Automatically flags accounts that exceed a defined transaction-per-minute threshold.
* **Low-Latency Signaling:** Optimized for minimal overhead, maintaining a p99 latency under **80ms**.

### Advanced Data Lakehouse
* **ACID Transactions:** Iceberg ensures that even at high speeds, data writes are reliable and never corrupted.
* **Time Travel:** Allows analysts to query the state of the data as it existed at any specific timestamp for post-mortem investigations.
* **Columnar Efficiency:** DuckDB reads from S3-backed Parquet files to provide instant query results without a traditional warehouse cost.

### Secure Automation
* **IaC Reliability:** **Terraform** manages the network isolation (VPC) and IAM roles needed to secure sensitive transaction data.
* **Dockerized Services:** Ensures the entire pipeline can be spun up locally for development with a single command.

## Scope

### In Scope
- **Fraud Logic Implementation:** Coding Flink jobs for location and velocity-based fraud detection.
- **Synthetic Data Engine:** Developing a robust generator that mimics real-world buying behaviors.
- **Automated Cloud Infrastructure:** Full Terraform/AWS orchestration.
- **Analytical Layer:** dbt models and DuckDB integration for forensic reporting.

### Out of Scope
- **Machine Learning Training:** The project focuses on heuristic and stateful rule-based detection rather than training neural networks.
- **Customer Notification System:** No automated email or SMS triggers for customers are included in this backend-focused pipeline.
- **User Interface:** The project provides a "Data Terminal" experience (CLI/SQL) rather than a graphical web dashboard.

## Success Criteria

1. **Throughput:** Process **25,000 events per second** with zero Kafka backpressure.
2. **Speed:** End-to-end latency from transaction generation to Iceberg commit under **80ms**.
3. **Accuracy:** The system correctly flags 100% of the "pre-programmed" fraud patterns generated by the synthetic stream.
4. **Query Performance:** Forensic SQL queries via DuckDB return results in **under 1 second**.
